# 渠道接入需求基线(运营者视角)

> 工作笔记。站在跨境 B2B 中小卖家(运营者)立场,定义"要接哪些渠道、每个渠道现实里怎么接、UI 要设哪些流程"。偏需求,不偏视觉设计。

## 0. 核心思维框架

不要按"渠道 logo"列需求,按 **"询盘从哪来 + 该来源技术上能怎么接"** 列。难点不在列清单,在于不同来源的可接入方式与收发能力天差地别。

## 1. 询盘来源全景(按真实线索量)

| 来源 | 角色 | 典型占比 |
| --- | --- | --- |
| 阿里国际站(站内信 + RFQ) | 多数工厂/贸易商第一大线索源 | 30–50% |
| 邮件 | 万能枢纽:直客 + 各平台通知都落这 | 20–40% |
| WhatsApp | 线索转化/成交主战场 | 成交环节 #1 |
| 独立站表单 / 在线客服 | 投了 SEO/Ads/DTC 才有 | 5–20% |
| 企业微信 / 微信 | 老客关系维护、有中国联系人的买家 | 关系维护 |
| Made-in-China / 环球资源 | 二线平台,部分行业重要 | 5–15% |
| LinkedIn | 高客单工业品优质线索 | 高价值低频 |
| Meta(Messenger/IG)+ 各家 Lead Ads | 消费品/快消、广告线索 | 看投放 |
| 展会(广交会等) | 周期性批量线索(名片/扫码) | 阶段性 |

区域 IM:中东/拉美/欧洲/东南亚/印度/非洲=WhatsApp;俄语区=Telegram;日/泰/台=Line;韩=KakaoTalk。

## 2. 接入方式的"降级阶梯"

按来源能力从好到差降级,**任何来源至少能落到第 3/4 级,绝不漏线索**:

1. **原生 API**(实时双向):WhatsApp Cloud API、邮件 IMAP/SMTP、Meta Graph、阿里 Open Platform。
2. **Webhook 入站**(表单类):独立站表单、Lead Ads、在线客服 widget。
3. **邮件转发桥接**(平台无开放 API 时的万能兜底):平台询盘通知邮件 → 转发到 Closer 收件地址 → 按模板解析。阿里站内信、Made-in-China、环球资源、LinkedIn 通知多走这条。
4. **CSV 批量导入**:展会、平台后台导出。
5. **浏览器插件 / 人工**:既无 API 又无邮件通知时的最后手段。

## 3. 收发能力不对称(必须写死在需求里)

| 渠道 | 自动收 | 自动回 |
| --- | --- | --- |
| 邮件 | ✅ | ✅ |
| WhatsApp / Messenger / IG | ✅ | ✅(会话窗口/模板限制) |
| 独立站表单 / Lead Ads | ✅ | ❌(导到邮件/IM 回) |
| 阿里站内信 / 二线平台 | ✅(邮件桥接) | ❌ 多数只能回平台站内 |
| 展会 / CSV | ✅(批量) | ❌ |

**最重要结论**:很多 B2B 平台只能进不能自动回。产品不能假设"每渠道都能 AI 自动回"。对这类渠道,Closer 价值=接住+甄别+起草草稿,回复导到邮件/WhatsApp 或人工贴回平台。当前数据模型默认渠道双向,需在需求层修正(增加渠道"回复能力"字段:full / draft-only / none)。

## 4. 分期需求

**一期(MVP,覆盖 ~80% 线索):**
- 邮件 IMAP/SMTP(直客 + 平台通知兜底枢纽)。已具备。
- 独立站表单 webhook。已具备。
- WhatsApp Cloud API。已具备。
- **邮件转发桥接 + 平台模板解析**(阿里/MIC/环球资源站内信通知)。**新需求,价值最高成本最低**;配套"只进不回"标记。

**二期(放量):**
- 阿里国际站原生 API(RFQ + 站内信),Open Platform 有门槛,先桥接后原生。
- Meta 全家桶(Messenger + IG + Lead Ads),与 WhatsApp 共用 Graph。
- Lead Ads webhook(Meta/Google/LinkedIn)。
- 线索 CSV 批量导入(展会/平台导出)。
- 企业微信/微信。

**三期(按市场/品类):** LinkedIn、Telegram/Line/KakaoTalk、在线客服 widget、TikTok、电话/SMS。

## 5. 横向需求(比渠道清单更决定好不好用)

1. **跨渠道客户合并**:同一买家从邮件+WhatsApp+阿里来,按邮箱/电话/公司域名并成一个客户档案。B2B 刚需。
2. **接入降级兜底**:任何平台至少能"邮件桥接 + CSV"接住。
3. **合规与渠道条款**:WhatsApp 24h 会话窗口 + 模板 + 质量评级;Meta 政策;邮件 SPF/DKIM/DMARC + 反垃圾;GDPR/CAN-SPAM;AI 身份披露。
4. **成本意识**:WhatsApp 按会话计费,影响"要不要自动回"。
5. **多语言 + 时区**:自动识别买家语言;夜间 7×24 自主应答。

## 6. 待确认(影响二期优先级)

1. 目标买家主要区域?(决定 WhatsApp/Line/KakaoTalk/Telegram/LinkedIn 取舍)
2. 品类与客单价?工业高客单(阿里 RFQ/LinkedIn 权重高)vs 消费品(独立站/IG/FB 权重高)。
3. 目标用户现在询盘实际主要从哪来?(决定一期桥接先做哪个平台)

# 邮箱接入 · 详细流程(逐步核对中)

> 邮箱是一期重点,也是"既是直客渠道、又是所有平台通知兜底枢纽"的关键。这里定义 UI 要设哪些流程步骤。

## 邮箱接入的两种用途(UI 必须区分)

- **A. 直客销售邮箱**(sales@yourco.com):IMAP 收 + SMTP 发,**双向**。买家直接发邮件来。
- **B. 平台通知桥接**:阿里/MIC 等的询盘通知邮件 → 解析成询盘,**只进不回**。复用邮件基建,但属于"桥接"语义。

一期先打通 A;B 作为"邮件桥接"在分期一并规划。

## A. 直客邮箱接入流程(UI 步骤)

1. **选择连接方式**
   - OAuth(Gmail / Microsoft 365 / Outlook)——推荐,免密码、绕开 2FA/授权码痛点。**当前后端不支持,需新增。**
   - IMAP/SMTP 基础认证(授权码/app password)——任意邮箱可用,但 Gmail/Outlook/QQ/163 需先开 IMAP 服务并用"授权码"而非登录密码。**当前后端已支持。**

2. **选择服务商预设(关键易用性)**
   - 预设 Gmail / Outlook365 / Zoho / 腾讯企业邮 / 网易企业邮 / 阿里云邮 / QQ / Yahoo / 自定义,**自动填 IMAP/SMTP host/port/SSL**,用户只填邮箱+授权码。多数用户不知道自己的 IMAP 服务器。**当前无预设,需新增。**
   - 自定义:imap_host/port、smtp_host/port、username、password、SSL/TLS、收取文件夹 mailbox。**后端字段已具备**(imap_host/port 默认 993、smtp_host/port 默认 465、username、password、mailbox 默认 INBOX、use_ssl 默认 true、poll_enabled)。

3. **测试连接(保存前强制)**
   - 测 IMAP 登录(能读?)+ 测 SMTP 登录并给自己发测试信(能发?)。
   - 分方向显示通过/失败 + 可操作错误(认证失败→"请开启 IMAP / 使用授权码";host 不可达;SSL 端口不匹配)。
   - 入站不通不允许"连接"。**后端有 `test-delivery`(SMTP)与 `poll-email`(IMAP),但未做"保存前强制双向测试 + 友好报错",需在接入流程里编排。**

4. **配置收取范围(防止误吞)**
   - 选收取文件夹/标签(INBOX 或专门路由询盘的文件夹)。
   - 轮询开关与频率(当前为轮询;IMAP IDLE 近实时为后续)。
   - 过滤:只收未读、排除 noreply@/newsletter、**起始日期(首次连接不要把十年历史全吞成询盘)**。**起始日期/过滤为新需求。**
   - 去重:按 Message-ID/UID。**后端已有(message-id 去重)。**

5. **出站/回复设置**
   - 发件人显示名 + 签名(设计稿 tone 步骤有签名)。
   - **回复线程**:回信带 In-Reply-To/References,使买家侧正确归入同一会话。**当前 SMTP 仅设 Message-ID,未设 In-Reply-To/References,回复不串线程,需补。**
   - 投递率:从自有域名 SMTP 发信时,提示配置 SPF/DKIM/DMARC。**新需求(至少给提示)。**

6. **合规与 AI 行为**
   - 邮件页脚 AI 身份披露开关。
   - 敏感操作必转人工(强制护栏,locked)。

7. **确认上线**
   - 渠道卡片状态:已连接、最近收取时间、累计接入数、投递/凭证健康。**readiness/alerts 已能提供凭证缺失/过期/待轮换信号。**

## 邮箱接入的"必踩坑"(需求要提前规避)

1. **授权码 / 2FA**:Gmail/Outlook 已禁用基础密码登录 → 必须授权码或 OAuth。**这是邮箱接入第一大失败原因**,UI 必须引导,否则会神秘失败。
2. **服务商需先开 IMAP/SMTP 服务**(Gmail 设置里开 IMAP;QQ/163 开服务并取授权码)。
3. **正文解析**:从自由文本提取买家公司/联系人/意图(LLM 增强);**附件**(RFQ PDF、规格表)当前被忽略(attachments=[]),B2B 里附件常含关键规格,需求需覆盖。
4. **引用文本剥离**:解析时剔除被引用的历史邮件,别把整条 thread 当新内容。**当前未做。**
5. **共享邮箱/catch-all**:sales@ 多人共用 → 多询盘 + 分配。
6. **退信处理**(SMTP bounce)。

## 当前后端 gap 小结(邮箱)

- 已具备:IMAP 轮询、SMTP 发送、message-id 去重、基础认证、凭证密封/轮换、readiness 告警。
- 待补:OAuth、服务商预设、保存前强制双向测试编排 + 友好报错、收取起始日期/过滤、回复线程头(In-Reply-To/References)、附件解析、引用剥离、SPF/DKIM/DMARC 提示。

## 决策确认(2026-06-27)

1. 连接方式:**OAuth 与 IMAP/授权码都支持**(可分期,但都要做)。
2. 服务商预设:**要做**。
3. 起始日期防吞历史 + 回复串线程:**认可**。
4. 附件解析:**要做**(B2B 询盘规格常在附件)。

# AI 智能接入与邮件分诊机制(核心)

> 产品定位修正:Closer 是 **AI 分诊台**,不是邮件搬运工。核心价值是"智能接入"——在入口用 AI 判断"是不是值得跟的询盘、抽取结构化信息、定级、决定去向"。只做接入、其余靠人工 = 没有意义。

## 架构关键点:创建询盘前加一道分类闸门

- **独立站表单**:每条提交都是询盘,**无需分诊**,直接入库。
- **邮箱(及未来 IM/平台)**:内容极杂,**必须在"创建询盘之前"加 AI 分类闸门**。
- 当前流程 `邮件→网关→无条件创建询盘→评分` 需改为 `邮件→分诊判断→(是询盘才)创建→评分`。这道闸门是新的,是邮箱接入的灵魂。

## 邮箱噪音构成(为什么不能全接)

新买家询盘/RFQ(金子)、老客户在跟的订单/物流/投诉、平台通知(伪装成通知的线索)、newsletter/营销/SaaS 通知、自动邮件(物流/支付/银行/发票)、内部同事邮件、向你推销的供应商/求职/合作、垃圾钓鱼、退信、自动回复。全部当询盘 = 噪音淹没 + AI 成本爆炸。

## 分层分诊管道(便宜→贵,规则先行)

**第 0 层 预过滤(零成本,确定性,AI 之前)**
- 去重(Message-ID,已有)
- 头部归档:List-Unsubscribe/List-Id=newsletter;Auto-Submitted=自动回复;退信单独处理
- 黑白名单:自家域名=内部;已知 SaaS/物流/支付域名=通知;已知买家域名=优先
- 起始日期 + 收取文件夹范围
- 平台通知模板识别(阿里/MIC)→ 走桥接解析专路

**第 1 层 轻量判别(便宜信号)**
- 人写 1:1 商务信 vs 群发/自动(Precedence: bulk、营销 HTML 版式)
- 语言识别;线程归属(已在跟的会话回复→挂原会话,不新建);新发件人 vs 已知客户

**第 2 层 AI 分类 + 抽取(核心)** —— 只对"疑似商务、人写、相关"的邮件跑 LLM
- 意图分类:新询盘 / RFQ / 报价请求 / 老订单跟进 / 投诉 / 物流 / 供应商推销 / 合作 / 求职 / 垃圾
- 结构化抽取:公司、联系人、国家、产品、数量、目标价、incoterm、认证、交期
- 质量定级:复用已有 A/B/C 评分与信号
- 附件解析:RFQ PDF/Excel → 规格数量
- 先剥离引用历史 + 签名再分析;每项给置信度

**第 3 层 路由决策**
| 判定 | 去向 |
| --- | --- |
| 高置信新询盘 | 创建询盘 → 收件箱 + 评分 →(护栏内)AI 起草回复 |
| 低置信/模糊 | 「待确认」分诊队列,人工一键判定,绝不静默创建或丢弃 |
| 老客户/在跟订单 | 挂到客户时间线/原会话,标记往来,不当新线索 |
| 非询盘但相关(投诉/物流) | 客户时间线 + 通知,或单独队列 |
| 噪音(newsletter/推销/垃圾/内部) | 「其他/已归档」桶,自动归档,可搜索可恢复,不硬删 |
| 平台通知 | 桥接模板解析 → 询盘 |

**第 4 层 人工反馈学习**
分诊队列的人工操作反哺:自动更新黑白名单、补充分类样例。越用越准。

## 四个收件桶(运营者心智模型)

收件箱(已确认询盘)· 待确认(AI 拿不准,人工一键判定)· 老客户往来(挂到已知客户)· 其他/已归档(噪音,自动归档可恢复)。

## 成本与安全

- AI 只跑过预过滤的邮件 → 控制 token 成本,不给 newsletter 调 LLM
- 每卖家可调严格度:严格=只明显询盘自动建,余进待确认;宽松=更多自动建
- LLM 不可用降级到规则路径(确定性兜底,符合产品哲学)

## 可推广到所有渠道

`归一化 → 预过滤 → AI 分类抽取 → 路由 → 待确认/学习` 是**共享智能层**,各渠道只写适配器归一化成统一格式。WhatsApp/表单/平台都喂同一个大脑:一个分诊大脑,多个接入适配器。

## 待确认(分诊机制)

1. 「待确认」分诊队列:独立页面,还是收件箱里的一个筛选 tab?
2. 严格度默认值:首次接入默认"宽松(多进待确认,少自动建)"以建立信任,还是"严格"?
3. 反馈学习:一期就做黑白名单自动更新,还是先纯人工标注、学习放二期?
4. 老客户往来 thread:是否需要独立"往来"视图,还是只进客户时间线?
